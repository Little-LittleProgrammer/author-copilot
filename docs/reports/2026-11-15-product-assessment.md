# Author Copilot 产品反向评估

评估日期：2026-11-15。

本报告依据当前仓库的需求、路线图、交付记录及关键交互实现，并核对竞品官网与公开行业资料。产品定位、用户选择、优先级与增长路径属于分析判断。当前没有用户访谈、真实留存、付费转化或获客成本数据，不能据此认定产品市场匹配已经成立。

本次没有启动应用或取得当前界面截图，因此用户体验部分是交互代码与流程分析，不是视觉、可访问性或真实使用体验验收；没有重新运行功能测试。交付记录中的自动化验证只作为历史证据。

## 1. 核心判断

Author Copilot 已形成有价值的产品基础：本地作品管理、长篇创作资料、作品内 AI 协作，以及可审阅、可恢复的修改。它具备邀请真实作者内测的功能基础；发布可靠性仍须完成路线图中的验收。

当前最需要验证的是：作者是否愿意把正在创作的作品放进来，每周持续使用，并为它付费。现有证据主要证明功能覆盖和工程投入，尚不能证明这些商业结果。

建议把首发定位收敛为：

> 面向持续创作长篇小说的作者，提供本地保存、前文来源查找与可审阅 AI 改稿的创作工作台。

“减少维护前文和改稿的负担”可以成为后续深化方向。“自动理解全书”“永不忘设定”“自动检查所有伏笔”超过当前交付边界。

## 2. 专业视角：价值、差距与防御力

### 2.1 哪些能力有真实价值

| 当前能力 | 对作者的价值 | 产品判断 |
| --- | --- | --- |
| 本地 Markdown、常用格式导入导出、无需账号进入本地工作区 | 降低迁移顾虑，保留稿件控制权 | 有价值，但要让备份、恢复和完整搬走作品足够简单 |
| AI 修改审阅、整轮保留/恢复、版本历史 | 降低试改一段或一章的心理成本 | 适合作为首发演示重点；尚不足以证明优于所有竞品 |
| 摘要、事实的来源快照和作者确认 | 能追问“这个说法来自哪里”，保留作者对设定的裁决权 | 产品方向清楚，需要进一步降低维护成本 |
| 大纲、灵感、正文、AI 共用作品资产 | 减少在写作软件、聊天窗口和资料文档之间搬运 | 是否真正省事，需要用同一任务与作者现有流程比较 |
| 两级助手、Skill 与可控工具 | 支持逐步沉淀创作流程 | 对普通作者应优先呈现任务和结果，底层机制交给高级设置 |

### 2.2 最大的产品差距：长期理解的承诺与维护负担

当前章节摘要与事实候选从单篇已保存正文提取，需要作者审阅；事实需要逐条确认。来源变化可以被检查，但不等于自动修正全书知识。检索、原生文件工具与提示词可以帮助 AI 查找前文，不等于已经交付可靠的长期记忆、人物关系、时间线和一致性检查。[仓库依据：路线图](../roadmap.md)

对长篇作者，最终收益应是减少查资料、补上下文和返工。若作者需要不断逐章提取、逐条审核、主动选择引用、检查过期来源，维护成本可能抵消 AI 节省的时间。不能只以“生成了多少资料”衡量成功。

建议后续优先验证：

1. 在真实作品里提出跨章问题，答案能否给出正确、充分的原文证据。
2. 修改一处设定后，能否找到需要重新审阅的资料与相关正文。
3. 用户能否快速判断“已确认设定”“人物主观看法”“AI 推断”和“来源已变化”。

是否引入语义检索，应由真实问题的召回表现决定。关键词检索是否足够、人物别称和隐含线索是否漏检，都需要实际评测；不能仅凭使用 FTS5 判断质量。

### 2.3 工程优势需要转化成作者的收益

可以向作者表达“改坏了能恢复”“能看到改了哪里”“回答可以回到原文”。不宜要求首次使用者先理解 Git、分支、HEAD、Skill、上下文装配和模型协议。

现有英文文案中仍可见 Git、staging、HEAD、Agent 与授权范围等表达，说明有进一步整理用户语言的空间。此处是代码和文案层面的判断，没有经过界面可用性测试。

防御力暂时应按潜力理解。Git、Agent SDK、模型接入和资料库都可以被复制；更持久的优势可能来自中文长篇任务的效果、连续创作时的可靠性、低维护成本，以及作者长期积累的设定和工作习惯。尊重数据可携带性仍然必要。

## 3. 用户视角：谁会用，为什么留下

### 3.1 建议的首批用户

首批优先招募：已经有长篇在写、主要在桌面创作、经常需要回查前文、愿意尝试 AI、同时重视作者控制权的人。可以用“在写约 10 万字以上作品”作为招募筛选条件之一；这是研究条件，不是已验证的用户画像。

| 用户群 | 与当前产品的匹配 | 主要阻力 |
| --- | --- | --- |
| 已有长篇、设定较多的个人小说作者 | 优先验证 | 前文查找是否准确，维护资料是否真的省时 |
| 高频连载作者 | 值得分组验证 | 保存、输入、章节切换、跨设备和交稿效率要求高 |
| 刚开始写作的爱好者 | 可参与，但不宜代表核心需求 | 容易把期待集中在生成质量，持续创作与付费意愿待验证 |
| 专业编剧 | 现阶段匹配有限 | 幕/场结构尚不等于专业剧本排版与制作交付 |
| 写作团队 | 后续再拓展 | 当前缺少云同步与协作，不宜作为首发主张 |
| 拒绝将稿件发送给外部模型的作者 | 本地写作部分可能适用 | 本地存稿不代表 AI 在本地运行；需清楚说明传输范围 |

“全球作者、小说家、编剧、团队、长篇创作者”适合作为愿景。首发营销需要回答一种具体作者、一个高频任务和一个可见收益。

### 3.2 按首次使用流程反推阻力

| 流程 | 当前基础与风险 | 建议验证 |
| --- | --- | --- |
| 进入 | 支持无需账号进入本地工作区，起步阻力较低 | 用户是否能立刻理解稿件保存在哪里、AI 是否需要另行连接 |
| 导入 | TXT/Word/Markdown 导入与拆章有利于试用已有稿件 | 章节是否正确，缺失的 Word 格式是否符合用户预期 |
| 获得第一次收益 | 作品内 AI、资料和检索已经存在 | 能否在数分钟内找到一段正确前文，或完成一次有价值的改稿 |
| 持续写作 | 有保存、冲突保护、字数与目标 | 自动保存和未保存草稿恢复应优先核实和补齐 |
| AI 改稿 | 有授权、修改审阅和整轮恢复 | 用户是否能理解范围与费用；好坏修改混合时是否难以取舍 |
| 维护设定 | 单篇提取、逐条确认、来源状态 | 审核时间是否低于手动整理时间，过期提醒是否足够聚焦 |
| 交稿与离开 | 支持 TXT/Markdown/DOCX 正文导出 | 正文导出之外，能否完整备份并恢复作品、资料及必要历史 |

首次体验建议围绕已有稿件展开：导入一部作品，询问一个前文问题并查看来源，然后在一小段文字上体验修改与恢复。先让作者看见结果，再逐步介绍高级功能。此为建议流程，不代表已有完整引导。

### 3.3 最需要优先处理的具体风险：手写内容的保护

当前 `ProjectEditorTab` 用 React 状态保存正在编辑的正文；在检查到的正文调用链里，写盘通过保存按钮或 Ctrl/Cmd+S 触发。切换章节时，若有未保存修改，现有逻辑询问是否放弃后继续。未发现正文自动保存或未保存草稿持久化的实现。[代码依据](../../apps/desktop/src/renderer/src/features/editor/ProjectEditorTab.tsx)

这不等于没有关闭确认、原子保存或 AI 任务恢复；这些保护已经存在，但保护的对象和时机不同。对于日常写作，作者预期自己的刚写内容也能在异常退出后恢复。

建议 P0 收口时先明确自动保存策略、可见状态、冲突处理和独立草稿恢复，再继续增加附加 AI 功能。至少验证中文输入法组合输入、长章编辑和异常退出后的恢复；正常关闭时的确认不能替代崩溃恢复。

本地版本历史也不能覆盖设备损坏、丢失等风险。即便云同步暂缓，整部作品的一键备份与恢复仍值得优先验证。

## 4. 市场视角：竞争已经存在，机会需要收窄

### 4.1 用户实际在比较什么

| 竞争对象 | 已有吸引力 | Author Copilot 需要证明的收益 |
| --- | --- | --- |
| 已有编辑器配合通用 AI 聊天工具 | 习惯成熟，可以渐进使用 AI | 少复制上下文、少返工，作品资料可以连续积累 |
| 番茄等平台作家工具 | 已位于创作和发表流程内，并有 AI 辅助 | 独立于单一发表平台、可携带的作品资产和更受控的改稿 |
| 橙瓜等码字工具 | 多端同步、写作统计、人物卡片和创作辅助 | 高频长篇任务上有足够明显的效率提升 |
| Scrivener | 面向长篇写作的项目组织与桌面工具体系 | 中文长篇 AI 工作流与降低改稿风险 |
| Novelcrafter | Codex、作品组织与 AI 接入 | 本地作品控制、中文任务质量与更简单的持续维护 |
| Sudowrite | 面向小说的创作、改写、风格和系列连续性能力 | 可信的前文来源、可恢复修改及完整作品工作流 |

事实依据：[番茄 AI 写作工具说明](https://fanqienovel.com/writer/zone/article/7327136545129906238)、[橙瓜官网](https://mz.chenggua.com/iphone/)、[Scrivener 官网](https://www.literatureandlatte.com/store/scrivener)、[Novelcrafter Codex](https://www.novelcrafter.com/features/codex)、[Sudowrite 官方介绍](https://sudowrite.com/pricing)。表中对本产品应如何竞争的内容为分析判断。

因此，“支持 AI”“有大纲”“有事实库”不足以单独构成竞争优势。功能组合能否让同一类作者更快、更安心地完成同一任务，才是需要取得的证据。

### 4.2 可以确认的行业规模与不能确认的份额

中国作家网 2026 年 10 月 16 日刊载的大会报道援引中国音像与数字出版协会《2025年度中国网络文学发展报告》：2025 年网络文学市场营收 574.72 亿元，平台驻站作者总数 3373.02 万人，用户规模 6.46 亿人。[报道原文](https://image.chinawriter.com.cn/n1/2026/1016/c404023-40815904.html)

这些数字说明相关创作生态规模大。它们不能直接当作 Author Copilot 的软件付费市场：

- 6.46 亿用户是网络文学受众口径，不能视为写作工具买家。
- 平台驻站作者总数不等于去重、持续活跃、使用桌面且愿意付费的个人作者数。
- 网络文学营收不等于作者软件支出，也不能按固定比例切给本产品。

本次未找到可以统一比较 Author Copilot、Novelcrafter、Sudowrite、橙瓜等产品的可靠活跃用户或付费收入份额数据；当前仓库也没有提供本产品的实际用户与收入数据。因此不能诚实地给出“目前占有多少”或“将获得百分之几”的结论。

建议后续分别定义：

- 活跃使用份额：目标市场中，实际使用本产品创作的去重作者占比。
- 付费作者渗透率：目标市场中，向本产品付费的去重作者占比。
- 收入份额：同一地域、同一时间和同类软件支出口径下的收入占比。

作者可能同时使用多个工具，活跃用户覆盖率可以重叠；软件收入与代收模型费用也应区分。

第一步应验证一个可触达的作者群体，而不是用行业总量乘一个预期占比。若未来调查得到了可靠的目标群体人数，再计算渗透率；当前不能填造分母。

### 4.3 更现实的市场进入路径

建议先以中文桌面长篇个人作者作为工作假设，英文界面保留，暂不同时承诺多个区域、编剧和团队市场。这个选择来自当前产品能力与可集中验证的任务，不代表已经证明中文市场更容易盈利。

首批获客可以围绕作者社群、长篇创作课程和真实案例招募，演示“已有作品中找证据、改一段、恢复”的任务。后续用用户续用和转介绍判断渠道质量。没有实际渠道数据前，不应预言低获客成本或自然增长。

可测试的市场表达：

> 写到后面，前文依然找得到；想改一稿，也能看清修改并恢复。

它与当前功能较一致。更强的“一致性检查”和“自动维护全书设定”应在交付并验证后再成为主宣传。

## 5. 付费与可持续性

Novelcrafter 官网目前列出每月 4、8、14、20 美元四档，8 美元档开始支持自带密钥 AI；模型成本取决于用户接入的供应商。[官方定价](https://www.novelcrafter.com/pricing)、[AI 费用说明](https://www.novelcrafter.com/help/faq/ai-and-prompting/ai-cost)。其费用说明含历史模型报价，不应直接套用为当前成本。

Sudowrite 采用订阅与额度方案；网页同时有月付和年付选项，具体结算价格应以选择后的页面为准。[官方方案](https://sudowrite.com/pricing)

这些方案证明市场已有不同付费结构，不能证明本产品可以获得同等客单价或付费转化。建议通过真实付费试验比较“软件权益 + 自带密钥”和“软件权益 + 托管模型服务”。若测试年费或订阅价格，明确为研究报价，不作为已确定定价。

普通作者需要低配置门槛，熟悉模型的用户可能重视自带密钥。两条路径可以共存；默认路径应依据首批用户选择，而非开发者偏好。

商业指标应同时看：净收入减模型成本、支付手续费、基础设施和支持等直接成本后的贡献，以及使用频次、任务质量和续费意愿。模型输出字数和对话次数不能独立证明价值。避免在成本和使用分布不明时承诺无上限 AI。

在线支付当前未开放，服务端 checkout 仍明确返回不可用。[代码依据](../../apps/api/src/platform/platform.controller.ts) 受邀免费内测和公开收费发布具有不同前提；收费上线需要完成真实支付、结算和故障链路，不能用余额界面替代商业闭环。

## 6. P0 收口与后续验证顺序

这里的优先级指下一步决策顺序，不是把所有建议都追加进本轮 P0。

| 优先级 | 事项 | 验证目标 |
| --- | --- | --- |
| 发布前 | 正文自动保存、未保存草稿恢复、完整作品备份恢复 | 作者的手写内容和作品资产能被可靠保护 |
| 发布前 | 最新版本真实模型、网络中断、取消恢复与目标安装包验收 | 自动化模拟之外的真实使用链路可靠 |
| 首轮内测 | 一条清晰的导入—前文问答—改稿—恢复路径 | 新用户能在少量指导后获得第一次价值 |
| 首轮内测 | 明确 AI 连接、发送内容、费用与能力边界 | 用户知道使用条件，不把本地存储理解成模型本地运行 |
| 收费前 | 支付、用量核对与服务支持 | 能真实收费并处理失败与差异 |
| 留存验证后 | 按痛点排序改进资料维护、逐块审阅、设定关联或同步 | 将开发资源投入已经观察到的高频阻力 |
| 后续探索 | 宠物、广告、漫剧、广泛协作与多品类扩展 | 有独立用户需求与商业证据后再立项 |

在功能进一步扩张前，应验证两条完整任务：

1. **前文查询**：导入真实长篇，回答跨章问题，展示原文证据，能承认没有足够依据。
2. **安全改稿**：对限定文本修改，作者看懂改动、保留或恢复，异常退出后状态可解释且能继续处理。

## 7. 建议的首轮研究与决策门槛

招募 15—20 名符合条件的作者，用自己的作品连续试用四周；尽量让一部分作者没有直接参与开发，单独记录提供过多少人工帮助。小样本适合发现任务障碍，不能代表市场转化率。

可以预先约定以下试验门槛。这些是内部决策标准，不是行业平均值或增长预测：

| 指标 | 建议定义与初始门槛 |
| --- | --- |
| 激活 | 首次进入后 24 小时内导入/创建真实作品，并独立完成一次有来源的问答或审阅改稿；争取至少 70% 完成 |
| 每周创作使用 | 一周至少两天，在真实作品里完成保存正文、核对前文或审阅改稿等任务，不能只计算打开应用 |
| 四周持续使用 | 初始 20 人中至少 8 人在第四周仍达到上述使用定义；同时按人数和比例报告 |
| 任务净收益 | 对比原有方法，记录查找、等待、审核和返工总时间，并由作者评价结果质量 |
| 事实维护负担 | 一章资料的审核时间、候选保留率、错误纠正量、来源变化后的返工时间 |
| 真实付费 | 在权益和价格明确后争取至少 5 笔自愿真实付款；付款前的口头意愿单独记录 |
| 可靠性 | 不可恢复内容损失作为停止扩量并优先处理的事件；报告失败和恢复结果 |

四周内应特别记录：用户是否回到旧工具、回去的具体任务是什么，以及 Author Copilot 是否只被当成偶尔打开的 AI 工具。辅助工具也可能成立，但其频次、定价和市场表达与主写作工作台不同。

若作者持续使用且愿意付费，再扩大到更多同类作者，估算渠道成本、支持成本与续费。若激活后不再回来，优先修复核心任务，不用更多功能替代留存问题。

## 8. 最终判断

现阶段值得继续投入，并尽快用真实作者验证。最有希望的方向，是服务一类持续写长篇、需要前文依据并重视改稿控制权的个人作者。

P0 功能即将完成意味着可以进入产品假设验证阶段。市场空间、规模化获客和可持续付费都还需要新的证据；当前应优先获得一批真正把作品和日常创作放进来的作者。
